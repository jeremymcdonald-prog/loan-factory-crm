# Decisions

Purpose: the running log of product and architecture decisions made during Phase 0 planning, with rationale, so the implementation team never has to guess why. Status values: **Locked** (build to this), **Proposed** (needs Jeremy's sign-off), **Deferred** (decided not to decide yet), **Superseded** (replaced by a later decision — the row stays for the record). See [[Open_Issues]] for questions still unanswered.

| # | Decision | Status | Rationale |
|---|----------|--------|-----------|
| D-01 | The existing offline HTML CRM prototype is **replaced, not evolved** | Locked | It is a single-file mock email-marketing tool with no backend, no persistence, no pipeline, no loan model, and zero reusable application logic. Rebuilding costs less than untangling it. Its good interaction ideas (one-tap AI suggestion cards, plain-language trigger cards, allowance meter) are carried into the new design. Evidence in [[Current_State_Audit]]. |
| D-02 | Default landing screen is **Today**, a command center — not "Home" | Locked | The core product thesis: the system tells the user what to do next. Every other decision serves this. |
| D-03 | Primary navigation is the 10-item action-based structure (Today, Pipeline, People, Partners, Conversations, Marketing, Automations, Intelligence, Team, Settings) | Locked | Action-based beats feature-based nav for cognitive load; validated against the brief and the TERA+ usability standard. Reporting lives inside Intelligence to avoid an 11th item. |
| D-04 | The AI layer is named **Ally** and is ambient across every screen — never a standalone chatbot | Locked | Extends Loan Factory's existing "Ally" automation concept (team marketing knowledge pack), so the name carries internal recognition. One consistent "Ally card" UI pattern everywhere. |
| D-05 | **Ally prepares, the human approves**: no borrower-facing communication ever sends autonomously in v1; every AI action is logged and attributable | Locked | Compliance (TCPA/CAN-SPAM/fair lending), trust-building with LOs, and mortgage-industry risk posture all point the same way. Tier model in [[Automation_Catalog]]. |
| D-06 | The CRM opportunity lifecycle is the locked 20-stage model grouped into ENGAGE / QUALIFY / TRANSACT / RETAIN / GROW — stage and milestone facts are CRM visibility data, entered by the team in v1 (future read-only sync from external systems is possible; the CRM never owns loan-of-record data) | Locked | Matches the brief and real broker-shop flow; grouping keeps the pipeline board usable (5 macro-columns with drill-in) instead of a 20-column wall. Full map in [[Mortgage_Workflow_Map]]. Boundary per D-22. |
| D-07 | The 135-template mortgage communication framework becomes the product's communication content layer, keyed to lifecycle stage | Locked | Highest-value reusable asset discovered. Templates ship stage-aware (connected to borrower stage, milestone, urgency) — never a flat template gallery. |
| D-08 | English + Vietnamese are first-class from early phases; per-contact language preference in the data model from day one | Locked | Loan Factory's LO base and the source materials (5-language persona framework, Vietnamese translation standards in the template library) prove demand. This is a differentiator competitors ignore. |
| D-09 | Recommended stack: Next.js + TypeScript, Supabase Postgres with row-level security + pgvector, Anthropic Claude via a model gateway, n8n as the automation backbone hidden behind a first-party Automations UX | Locked (technical; not Jeremy-facing) | Fastest credible path with strong tenant isolation and AI memory support; n8n already exists in Jeremy's stack. Rationale in [[Technical_Architecture]]. |
| D-10 | Phase 1 does **not** depend on any external integration (no LOS, no POS, no credit) | Locked | The #1 schedule risk for CRM builds is gating core UX on vendor integrations. Phase 1 runs on manually/CSV-entered and form-captured data; future data connections (read-only sync in, communication out) layer in from Phase 2+. See [[Integration_Map]]. |
| D-11 | AI scoring uses documented, fair-lending-safe factors only (behavioral + file-progress signals; no protected classes or proxies), with a periodic disparate-impact review | Locked | Non-negotiable compliance posture. Factor documentation lives in [[AI_Product_Architecture]]; review cadence in [[Mortgage_Compliance]]. |
| D-12 | Working name **Loan Factory CRM** | Locked | Originally proposed as the codename "Foundry"; Jeremy's 2026-07-16 scope directive retired the codename and locked the working name **Loan Factory CRM**. Nothing in the build depended on the codename; the final market name and any licensing display requirements remain a branding-only call. Resolves [[Open_Issues]] Q6. |
| D-13 | Design direction: elite command-center aesthetic, light + dark themes, high information density done calmly, status colors tied to loan urgency; the coral/beige/pastel/emoji direction of the prototype is retired | Locked | The brief's branding requirements plus the audit's diagnosis. Full token system in [[Design_System]]. |
| D-14 | The marketing-content-os repo is used as **knowledge content** (brand rules, compliance guardrails, prompts, briefs) — its archived app prototype is not revived | Locked | The repo self-describes as markdown-first, "not a web product"; the archived app was already abandoned once. Its compliance corpus (do-not-say, required disclosures, state rules) becomes Ally's guardrail content. |
| D-15 | TERA+ persona/scenario framework (111 personas, 259 scenarios) is adopted as the QA and usability-testing backbone | Locked | Purpose-built, multilingual, already aligned to Loan Factory users. Saves weeks of QA design. See [[QA_Plan]]. |
| D-16 | Borrower portal ships as a Phase 3 concept, not earlier | Superseded → D-23 | Superseded by the 2026-07-16 CRM-only scope correction: the borrower portal is removed from every phase. Borrowers are CRM contacts, not product users; borrower personas remain only as source material for communication content and QA. See D-23. |
| D-17 | TERA+ materials are **source material only**: the persona/scenario corpus feeds [[User_Personas]], usability scorecards, and QA scenarios ([[QA_Plan]], D-15) — this CRM does not replace, feed, or compete with the TERA+ platform effort | Locked | Originally deferred pending a conversation with Jeremy. The 2026-07-16 CRM-only boundary (D-22) resolved it without one: there is no positioning question to settle, and TERA+ is never an implementation dependency. Closes [[Open_Issues]] Q1. |
| D-18 | The safe-automation tier vocabulary (T0 never-automated → T3 fully automated internal) is defined **once**, in [[Automation_Catalog]] §1; every other document adopts it verbatim | Locked | The critique pass caught two documents using inverted tier ladders — a real autonomous-send risk if engineers follow the wrong one. One canonical ladder, everywhere. |
| D-19 | The AllyCard verdict set is defined **once**, in [[Design_System]], and used verbatim on every surface: Approve & send · Edit then send · Reject (with structured reason) · Snooze · Reassign | Locked | The same critique class: three screens had invented their own approval verbs. Rejection reasons are structured because they feed Ally's learning loop ([[AI_Product_Architecture]]). |
| D-20 | Today's work queue uses the 10 priority classes specified in [[Screen_Specifications]] Part 1 (Screen 1) as the canonical urgency taxonomy; Notification lanes and Pipeline risk flags derive from it rather than defining rivals | Locked | Critique found three competing urgency taxonomies across surfaces — a direct threat to the toddler-simple standard. One taxonomy, derived views. |
| D-21 | Batch approval ships **Phase 2**, only for Routine (fully-automated-tier, lint-clean, identical-template) items, with sampled review; sensitive topics can never be batched | Locked | Single-item trust must be established before batch trust; sensitive topics (rate lock, cash-to-close, payment change, delays, adverse outcomes) always get a forced full read. |
| D-22 | **CRM-only product boundary.** Loan Factory CRM is an AI-powered mortgage CRM — nothing more. It does not originate, underwrite, approve, price, disclose, process, or service loans. It is **not**: an LOS, a POS, a borrower portal, a loan application platform, an underwriting platform, a document collection system, a pricing engine, a mobile application suite, a replacement for TERA+, or a general Loan Factory platform | Locked | Jeremy's 2026-07-16 scope directive. The dividing line: communication and relationship work triggered by loan facts is in scope (e.g. a docs-needed follow-up email to a borrower); performing the loan work is out of scope (collecting/storing loan documents, managing underwriting conditions as a work surface, generating disclosures, pricing scenarios, 1003 intake). Every document conforms to this boundary. |
| D-23 | Borrower portal and native mobile apps (iOS/Android, app stores) are **removed from every phase**; responsive web on desktop and mobile browsers is **required** | Locked | Same 2026-07-16 directive. Borrowers are CRM contacts, not product users; borrower personas remain as source material for communication content and QA. Supersedes D-16. Responsive-web behavior specs stay first-class in [[Design_System]] and [[Screen_Specifications]]. |
| D-24 | Official repository: `git@github.com:jeremymcdonald-prog/loan-factory-crm.git` | Locked | Named by Jeremy 2026-07-16; the Phase-1 walking skeleton starts here ([[Next_Actions]]). |
